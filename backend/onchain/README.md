# On-chain verification of Huma pages

`HumaPagesV4` verifies a Huma page on Base and records it. It checks everything Huma's reader checks: every
zero-knowledge proof, and everything the reader verifies besides the proofs. The six proof verifiers are generated by
Barretenberg (`bb write_solidity_verifier -t evm --optimized`) from Huma's **existing** long3 circuits (chunk and final
for each page size: 1024, 4096 and 10000 characters). No circuit is changed or added.

What HumaPagesV4 checks, as `backend/integrations/noir/long/reader.mjs` does for v3 and v3-passkey pages:

1. **Every proof.** Each part's proof and the final proof go to the verifiers for the page's size.
2. **Parts.** The genesis part comes first and only first, each part starts where the last ended, and the final state
   is where the last part ended.
3. **Statement bounds.** The journal's sanity rules: nonce halves under 2^128, consistent counts, times in range, and so
   on.
4. **Writer key.** The page's P-256 capture key signed every checkpoint and check-in root, in order. This uses Base's
   P-256 precompile, RIP-7212 at `0x100`. The Poseidon2 event digest of (kind, root) must equal the statement's; there
   must be `checkpoint_count` checkpoints and `approved` check-ins, ending with a checkpoint.
5. **Nonce ↔ key.** `nonce[1] = Poseidon2(NONCE, device_root(key), nonce[0]) mod 2^128`, so another key can't sign the
   same roots and claim the page.
6. **Passkey pages.** Every approved check-in needs a WebAuthn assertion by the page's passkey for `https://huma.social`:
   - over `SHA-256(PRESENCE domain ‖ root)`;
   - user present and verified;
   - counters rising;
   - not cross-origin;
   - bound to the page by the writer key.

It then records `keccak256(statement) → (block, parts, tier, events, passkey, submitter)` and emits `PageVerified` with
the key's hash. The text itself isn't on-chain: the statement holds its commitments, and whoever has the text checks it.

How it runs:
- **Browser.** It proves a page as before. After Finish, **Verify On-Chain** proves the same page again in the EVM
  format: the same circuits, with a keccak transcript (`frontend/write/prove.mjs` `proveForChain`). It sends those proofs
  and the page proof, whose signed events the contract checks. The writing never leaves the browser.
- **Server.** The relayer wallet submits for the writer (`frontend/onchain.mjs`, `POST /api/onchain/pages`), so writers
  need no wallet or gas. Each call is simulated first, so a page that wouldn't verify costs nothing.
- **Batches.** A page of up to 12 parts and 64 events goes in one transaction (`submit`). A longer one uses
  `submitParts` and `submitEvents` batches, closed by `submitFinal`.
- **Reading it back.** `/verify` shows **Verified on-chain** for a recorded page, with the transaction and a `cast`
  command to ask the contract yourself.

`HumaPoseidon2` is Huma's Poseidon2 sponge (`src/Poseidon2.sol`) as its own contract, which keeps HumaPagesV4 under the
size limit. `HumaPagesV3` (proofs and linkage only) remains deployed; V4 replaces it.

`node audit.mjs` reads the chain and runs 51 checks; it sends nothing. It checks that:
- the code of V3, V4, HumaPoseidon2 and the verifiers is byte-identical to this folder's build;
- the wiring is right;
- every verifier accepts a real proof of its size and rejects it with a bit flipped;
- HumaPoseidon2 equals the reader's Poseidon2;
- every recorded page is there;
- the deploy transactions succeeded.

## Use

Install `forge-std` into `lib/` once (`forge install foundry-rs/forge-std --no-git`). Then:

```sh
forge test     # 54 tests: real EVM proofs and signed events of all three page sizes, Poseidon2 vectors, passkeys
forge build && HUMA_RELAYER_KEY=0x… node deploy.mjs --yes      # the 6 verifiers + HumaPagesV3
forge build && HUMA_RELAYER_KEY=0x… node deploy-v4.mjs --yes   # HumaPoseidon2 + HumaPagesV4 on those verifiers
node scripts/evidence-fixtures.mjs <dir with long-case-*.json>  # rewrite test/fixtures/*/page-proof.json, evidence.json
```

In the tests, Base's P-256 precompile is stood in for by Daimo's P256Verifier, which takes the same input and gives the
same answers. It is placed at `0x100`, using its runtime code from Base Sepolia (`test/fixtures/p256-verifier.hex`).

To turn it on, set these in the server's env (`.env.example`):
- `HUMA_RELAYER_KEY`;
- `HUMA_ONCHAIN_CONTRACT`, the HumaPagesV4 address;
- `HUMA_CHAIN`, which defaults to `base-sepolia`.

`keys/` holds the EVM verification keys. They are pinned in `frontend/write/pins.mjs` (`EVM_KEYS`), and
`write/build.mjs` copies them into `dist/write`.
